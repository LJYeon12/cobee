# 하니스 유지보수

[문서 목차](README.md) · [개발 절차](development.md) · [검증 기준](verification.md)

탈퇴 관련 기준일은 2026-10-31이다. 다른 항목의 이전 검증 날짜는 유지한다.
코드·설정·계약을 바꾸는 작업에서 관련 문서를 함께 갱신한다. 별도 자동 실행은 설정하지 않는다.

## 변경 뒤 문서 확인

1. [개발 절차의 갱신 표](development.md#변경별-확인-범위)에서 영향을 받는 문서를 고른다.
2. 문서의 경로, 설정 이름, 명령을 현재 소스와 대조한다.
3. 코드 확인과 실행 확인을 구분한다. 실행하지 않은 결과를 성공으로 옮겨 적지 않는다.
4. 링크, 앵커, 코드 블록 문법과 문서 예제를 검사한다.
5. 검증을 다시 수행했으면 환경·명령·결과·날짜를 [검증 기록](verification.md#마지막-검증-기록)에 반영한다.
6. 새 문서가 생겼으면 [목차](README.md)와 관련 AGENTS에서 연결한다.

기록이 오래되었거나 원본이 달라졌으면 확인 전까지 이전 실행의 근거로만 사용한다.

검증 CI와 전체 런타임 준비는 아직 수행하지 않은 작업이다.
완료 근거 없이 항목을 닫지 않는다.

## Graphify 수동 관리

[공통 Graphify 규칙](../AGENTS.md#graphify)을 기준으로 한다.

- 코드 변경만으로 그래프를 재생성하지 않는다.
- 기존 그래프는 범위를 좁히는 데 사용하고 원본 코드로 확인한다.
- 포맷 변경만으로도 소스 해시가 달라질 수 있다. 해시 차이가 곧 관계 오류를 뜻하지는 않는다.
- `reviewed-links.json`의 소스 해시가 달라졌으면 관련 관계를 다시 검토한다.
- 갱신을 요청받았을 때 기존 제외 범위와 수동 재생성 순서를 유지한다.
- 문서 추가도 자동 갱신의 계기로 사용하지 않는다.

## 새 문서와 결정 기록

작업 순서·명령·제약은 해당 상세 문서에 적는다.
되돌리기 어려운 실제 설계 결정을 내렸을 때는 배경, 대안, 선택, 결과를 ADR로 남긴다.
아직 정하지 않은 정책은 확인 필요 항목으로 유지한다.
