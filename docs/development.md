# 개발과 문서 갱신 절차

[문서 목차](README.md) · [구조 안내](architecture.md) · [검증 기준](verification.md)

## 작업 시작

1. 공통 규칙과 해당 패키지의 AGENTS를 읽는다.
2. 요청한 결과, 변경할 파일, 완료 조건을 짧게 정리한다.
3. 구조 질문은 기존 Graphify로 범위를 좁히고 원본 코드를 확인한다.
4. 실행 환경과 현재 검증 상태를 확인한다.
5. 아래 표로 필요한 문서와 테스트를 고른다.

여러 단계가 있거나 두 패키지를 함께 바꾸는 작업은 계획을 남긴다.
계획에는 목표, 범위, 순서, 검증, 미해결 사항을 적는다. 필요한 작업에서 `.local/plans/`를 만들고 문서 목차에서 연결한다.

## 구현과 검증

- 기존 패턴을 먼저 따른다. 테스트를 위해 분리가 필요하면 작은 계산 모듈이나 주입 가능한 의존성부터 검토한다.
- 단위 테스트에는 실제 계산·검증 로직을 사용한다. DB, HTTP, 스케줄러는 테스트에 필요한 가짜 값이나 대체 수단을 쓴다.
- 결과가 없는 앱 구동 확인만으로 업무 로직이 검증됐다고 판단하지 않는다.
- [변경별 검사 범위](verification.md#변경별-검사-범위)를 실행한다. 실패가 있으면 원인과 범위를 확인한다.
- 단위 검사와 통합 실행을 구분한다. 서버 시작, 동기화, 학습은 대상 환경과 요청 범위를 확인한다.
- 코드나 설정을 바꿨으면 같은 작업에서 관련 문서를 갱신한다.

## 문서 작성 기준

- 명령에는 작업 위치와 준비 조건을 적는다.
- 현재 구현, 실행 확인, 제안·미확인을 구분한다.
- 검증 기록에는 날짜, 런타임, 실제 명령, 결과, 한계를 적는다.
- 코드를 다시 설명하는 긴 문서보다 원본 위치와 중요한 제약을 연결한다.
- 새 문서는 [목차](README.md)와 관련 문서에서 연결한다.
- 실제 비밀번호, 키, 개인정보를 예제에 넣지 않는다.

가벼운 선택의 이유는 해당 문서에 짧게 적는다.
실제 대안이 있고, 되돌리는 비용이 크며, 배경 없이 이해하기 어려운 결정은 ADR로 남긴다.
그 결정이 생긴 시점에 `docs/adr/`와 목차를 만든다. 과거 설계의 이유를 추측해서 쓰지 않는다.

## 작업 완료

- 요청한 동작과 범위가 충족되었는지 확인한다.
- 실행한 검사와 결과를 확인한다. 미실행 항목과 남은 경고를 구분한다.
- 문서 링크, 명령의 대상, 환경 변수 이름을 확인한다.
- 요청하지 않은 설치·외부 연결·자동 실행 설정이 추가되지 않았는지 확인한다.
- 변경 내용, 검증 결과, 남은 한계를 보고한다.

Graphify 갱신은 별도 수동 요청을 따른다. 코드 변경만으로 자동 재생성하지 않는다.
